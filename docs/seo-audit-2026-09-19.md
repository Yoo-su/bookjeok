## 결론

주요 페이지의 기본 색인·공유 기반은 정상이다. 점검한 한국어 페이지는 200, 페이지별 title/description/canonical/OG를 제공하고, 도서·판매·리뷰 상세 본문이 서버 HTML에 들어 있다. 사이트 전체를 막는 robots/noindex 사고는 발견하지 않았다.

먼저 고칠 것은 **판매 상태 및 평점 구조화 데이터 오류**, **SSR 프리패치 실패 감지 누락**이다. 다음으로 오래된 콘텐츠의 발견 경로와 라운지 초기 HTML을 보강한다. 공유 이미지 미수신은 표본에서 없었지만 페이지별 카드 표현은 개선 여지가 있다.

이 결과는 기술적 수집 가능성 점검이다. Search Console·네이버 서치어드바이저의 실제 색인 수, 제외 사유, 노출·클릭·검색어, 실제 SNS 앱의 카드 캐시는 확인하지 않았다. 순위·색인·리치 결과 노출을 보장한다는 의미가 아니다.

## 우선 수정할 결함

### 1. 판매 완료 상품이 InStock으로 선언된다 — P2, 코드 재현

- 위치: `apps/web/src/features/book-sale/components/common/book-sale-json-ld/index.tsx:16`.
- 실제 enum: `packages/core/src/features/book-sale/types.ts:6`의 `FOR_SALE / RESERVED / SOLD`.
- 매핑 구현은 `AVAILABLE / RESERVED / SOLD_OUT`을 비교한다. 로컬 함수 추출 실행 결과:

```text
FOR_SALE -> https://schema.org/InStock
RESERVED -> https://schema.org/LimitedAvailability
SOLD     -> https://schema.org/InStock
```

운영에서 조회한 판매글 3개는 판매 중이어서 SOLD 운영 표본 재현은 하지 않았다. **SOLD 입력에 대한 코드 오동작은 확정**이다. 공용 `SaleStatus` enum으로 매핑하고 판매 완료는 `SoldOut`으로 수정한다. 판매 상태를 공유 설명에도 포함하면 오래된 거래글 공유 시 오해를 줄일 수 있다.

Google Product 스니펫은 가격·재고를 전달하는 구조화 데이터다. [공식 Product 문서](https://developers.google.com/search/docs/appearance/structured-data/product-snippet).

### 2. 0.5점 리뷰가 선언된 평점 범위를 벗어난다 — P2, 운영 재현

- 위치: `apps/web/src/features/review/components/common/review-json-ld/index.tsx:33`.
- 운영 URL: `https://bookjeok.com/ko/book/reviews/15`.
- 실제 JSON-LD: `ratingValue: 0.5, bestRating: 5, worstRating: 1`.
- 입력 UI는 0부터 5까지 0.5 단위를 허용한다. 현재 JSON-LD는 0점은 생략하고 양수만 출력한다.

0이 실제 평점인지 미평가 값인지 먼저 도메인 의미에 맞춰 정리한 뒤, `worstRating`을 실제 평가 척도와 일치시킨다. 0을 미평가로 쓰면 유효 최저점은 0.5, 0도 평가라면 0이 된다. 별점 리치 결과의 유효성 문제이며 **페이지 전체가 색인되지 않는다고 단정하지 않는다**. [Google 평점 척도 정의](https://developers.google.com/search/docs/appearance/structured-data/review-snippet).

### 3. SSR 프리패치 실패를 감지하지 못하고 빈 섹션을 캐시할 수 있다 — P2, 로컬 재현

- 위치: `apps/web/src/shared/components/server-query-boundary.tsx:45`.
- `prefetchQuery` / `prefetchInfiniteQuery`를 `Promise.allSettled`로 감싸고 `rejected`일 때만 로그를 남긴다.
- 이 API들은 fetch 실패를 reject하지 않는다. 설치된 라이브러리로 고의 실패 쿼리를 실행한 결과 `promiseStatus=fulfilled`, `queryStatus=error`였다.
- 따라서 주석에 적힌 실패 로그가 일반적인 조회 실패에서 실행되지 않는다. failed query는 기본 dehydration에서 빠지고 페이지 렌더는 성공해, ISR에 실제 목록 대신 로딩/빈 섹션이 남을 수 있다.

핵심 목록은 `fetchQuery`/`fetchInfiniteQuery`로 실패를 전달하거나, 프리패치 후 쿼리 상태를 검사한다. 핵심 데이터 전체 실패 시 재생성을 실패시켜 기존 정상 ISR을 유지하고, 부가 섹션은 선택적으로 폴백한다. **이번 운영 조회에서 장애 상태가 관측된 것은 아니며 장애 처리 결함을 재현한 것**이다. [TanStack QueryClient 문서](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient).

## 정확성·리소스 관련 추가 결함

### 4. 상품 정보에 근거 없는 값을 넣는다 — P2, 운영 확인

`book-sale-json-ld/index.tsx:46`에서 모든 도서의 `brand`를 `bookjeok`으로, `priceValidUntil`을 렌더 시점 +365일로 지정한다. `/sales/20`, `/36` 운영 JSON-LD에서 확인했다.

북적은 이 책들의 상품 브랜드가 아니고 판매자가 1년간 가격을 보장한 것도 아니다. 실제 값이 없으면 선택 필드를 생략한다. 서버 렌더마다 날짜가 밀려나는 방식도 제거한다. 이는 정보 정확성 문제이며 이 두 속성 때문에 현재 색인이 막혔다고 판단한 것은 아니다.

### 5. 같은 리뷰의 비정규 URL이 별도 렌더·캐시 경로를 만든다 — P3, 운영 재현

`/ko/book/reviews/0078`은 301/308이 아니라 **200 + x-vercel-cache: MISS**로 리뷰 78을 렌더했다. canonical은 `/ko/book/reviews/78`로 정상이다.

원인: `book/reviews/[id]/page.tsx`에서 문자열을 `Number(id)`로 바꾼 뒤 정수 여부만 검사한다. 앞자리 0 등의 변형을 동일 리뷰로 받아들이지만 라우트 캐시는 URL별로 만들어진다. canonical은 검색의 중복 정리에 도움을 주지만 이미 발생한 렌더 비용은 없애지 못한다. 비정규 숫자는 미들웨어에서 정규 URL로 영구 리다이렉트하거나 일관된 404 정책을 적용한다. **대량 악용이나 실제 비용 증가량은 측정하지 않았으므로 낮은 우선순위**다.

### 6. SearchAction의 검색 파라미터가 실제 검색과 다르다 — P3, 코드 확인

`shared/config/json-ld.ts:17`은 `?keyword={search_term_string}`을 선언하지만 실제 검색은 `?q=`를 사용한다. 유지한다면 실제 검색 파라미터에 맞춘다.

단, Google은 사이트링크 검색창을 2024년 11월에 종료했다. 이 수정으로 Google 검색창이 생기거나 순위가 오를 것이라고 기대하면 안 된다. [Google 종료 공지](https://developers.google.com/search/blog/2024/10/sitelinks-search-box).

## 검색 발견성 개선

### 사이트맵 50건 제한과 무한 스크롤

- `app/sitemap.ts`는 리뷰·판매글 각각 `page: 1, limit: 50`만 조회한다.
- 운영 sitemap은 **154 URL = 정적 8 + 리뷰 50 + 판매글 27 + 연결 도서 69**.
- 리뷰 15는 공개 200이고 리뷰 홈에도 링크가 있지만 sitemap에는 없다. 따라서 **누락 = 미색인**이라고 판단할 수는 없다.
- 마켓 추가 목록은 `useInView → fetchNextPage`, 필터된 리뷰 목록도 같은 구조다. 리뷰 홈의 카테고리 더보기는 클라이언트 필터이며 서버 fallback은 기본 홈 목록이다.

오래된 글이 인기·카테고리 상위에서도 밀리면 발견 경로가 약해진다. 공개 리뷰·공개 판매글 전체를 포함하는 안정적인 sitemap을 먼저 만들고, 규모가 커지면 분할 sitemap으로 확장한다. 목록 탐색은 고유 URL과 실제 `<a href>`를 갖춘 페이지네이션을 병행할 수 있다. 페이지네이션을 추가하면 각 페이지의 서버 결과와 canonical도 일치시켜야 한다.

**비용 때문에 5.7만 도서 전체를 즉시 sitemap에 추가하는 것은 권하지 않는다.** 공개 리뷰·판매글에 연결된 도서, 실제 독서 활동이 있는 도서 등 우선순위를 정한다. Google은 사용자처럼 버튼을 누르거나 스크롤하지 않는다. [Google 페이지네이션 지침](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading).

### 라운지의 핵심 피드를 초기 HTML에 포함

`(default)/lounge/page.tsx:41`은 인기 도서와 활성 독자만 시딩한다. `LoungeFeedList`가 쓰는 무한 쿼리는 빠져 있다. 운영 HTML의 최신 피드 구간은 스켈레톤이고, h1은 없으며, 발견된 콘텐츠 링크는 사용자 프로필 3개였다. 인기 도서 카드의 클릭은 모달을 여는 동작이다.

최신 공개 피드 첫 페이지를 ISR 시딩하고 페이지 설명과 h1을 넣는다. 모달 안팎에 도서 상세로 향하는 실제 링크를 제공하면 도서 발견 경로도 생긴다. Google이 JS를 렌더해 피드를 볼 가능성은 있으므로 라운지가 전혀 색인될 수 없다는 뜻은 아니다. h1 부재 하나만으로 색인 차단을 주장하지도 않는다. [Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

## SNS 공유 결과와 개선

- `facebookexternalhit/1.1`, `kakaotalk-scrap/1.0` UA 표본에서 상세 OG가 `<head>`에 존재했다.
- 접두사 없는 `/book/reviews/78`도 카카오 UA에는 200으로 응답하고 정규 `/ko/…` OG URL을 제공했다.
- Twitterbot UA로 이미지 HEAD 요청: 도서 표지 WebP **200 / 74,600 bytes**, 판매 사진 JPEG **200 / 250,045 bytes**, 기본 로고 PNG **200 / 25,845 bytes**.
- 기본 로고 로컬 파일은 1200×630. 마켓·리뷰 홈·라운지는 서로 다른 제목/설명을 가지지만 이 로고 이미지를 공통으로 사용한다.
- 상세 페이지는 도서 표지 또는 판매 실물 사진을 올바르게 선택한다. 표본에서 이미지 부재·인증 요구·깨진 URL은 없었다.

개선 권장:

1. 마켓·리뷰·라운지의 성격을 구분하는 정적 공유 이미지 3장을 마련한다. 요청마다 동적 이미지 생성부터 도입할 필요는 없다.
2. `createPageMetadata`가 이미지를 URL 문자열 배열로 재정의하면서 전역 OG의 width/height/alt가 페이지 출력에서 빠진다. 실제 크기를 아는 자산은 객체로 전달하고 alt도 지정한다. 누락 자체가 공유 실패를 뜻하지는 않는다. [Open Graph 이미지 속성](https://ogp.me/).
3. 현재 기본 가로 로고는 `twitter:card=summary`, 책 표지는 `summary_large_image`다. 이미지 방향과 카드 형태를 함께 설계한다. 표지를 가로 카드에 넣을 때는 여백을 둔 캔버스가 선택지다. 실제 플랫폼별 자름 여부는 앱에서 확인해야 한다.
4. 리뷰 카카오 공유 버튼은 `Share.sendDefault`로 책명·저자만 전달한다. OG의 감상 발췌와는 별도 경로다(`review-detail/.../header.tsx:70`). 공용 공유 데이터 생성기를 쓰면 링크 붙여넣기와 버튼 공유의 내용이 일치한다. 판매글 SDK 설명도 OG에 있는 지역은 제외한다.

## 이미 잘 처리된 부분과 유지할 정책

- 한국어 주요 페이지의 자기 canonical, `/ko` 중심 hreflang, 미들웨어 중복 hreflang 헤더 제거.
- `/en/book/reviews`의 실제 `noindex, nofollow` 확인. `/en`의 robots 수집을 허용해 noindex를 읽게 하는 정책은 타당하다.
- 비공개 리뷰의 noindex와 공개 sitemap 필터는 코드에 존재한다. 비공개 운영 표본은 열람하지 않았다.
- 잘못된 리뷰 `/abc`, `/0`은 실제 HTTP 404. 메타태그 일부만 보고 soft 404라고 오판하지 않았다.
- 상세 메타데이터와 본문 데이터는 React cache를 공유한다. 도서 상세의 인메모리 캐시는 TTL·상한이 있다.
- 도서 상세 30일, 판매 상세 1시간, 리뷰 상세 24시간 ISR 설정. 도서 상세 표본에서 HIT, 목록에서 STALE 응답을 확인했다. STALE은 재검증 과정일 수 있어 장애로 판단하지 않았다.
- 대부분의 도서 목록 링크는 `prefetch={false}`로 대량 선렌더를 억제한다. 모든 캐시 주기를 줄이는 방향은 권하지 않는다.
- 도서 요약 시딩은 **저장된 요약 조회**다. 크롤링마다 LLM 요약을 생성하는 코드가 아니다.
- sitemap의 정적 URL에 가짜 lastmod를 넣지 않고 동적 글에는 updatedAt을 사용한다. RSS도 공개 접근 가능하고 표본 55개 item이 정상 XML로 파싱됐다.
- Googlebot·Yeti·Bingbot·SNS 크롤러 허용 목록이 존재한다. AI 검색/수집 봇과 일부 기타 봇 차단은 명시적 비용 정책이다. AI 검색 노출을 원한다면 별도 정책 재검토 대상이며 이번에 해제하지 않았다.
- User-Agent를 흉내 낸 HTTP 조회는 실제 플랫폼 IP/WAF 판정이나 실제 공유 앱의 캐시까지 검증한 것은 아니다.

## 검증과 후속 순서

1. 상태 enum·평점 범위·프리패치 실패 감지 수정. 해당 경계값 회귀 테스트 추가.
2. 공개 글 sitemap 누락 보완, 라운지 첫 피드 시딩 및 링크 보강.
3. 허구의 Product 필드 정리, 숫자 URL 정규화, 공유 문구·정적 카드 개선.
4. 배포 후 Google Rich Results Test로 판매 중/예약/판매 완료와 0.5/5점 리뷰를 재검증.
5. Search Console URL 검사·페이지 색인·실적 및 네이버 수집 현황으로 실제 결과 확인. 여기서만 미색인 원인과 검색 유입 문제를 확정할 수 있다.
6. 카카오·X·Facebook에서 실제 공유 미리보기 확인. 테스트를 위해 SNS에 게시하거나 메시지를 전송하지 않았다.

로컬 기존 테스트: metadata 4 + crawlers 9 + middleware 11 = **24/24 통과**. 설치된 Vitest를 직접 실행했다. 기존 테스트에 Product/Review JSON-LD의 위 경계값 검증은 포함되지 않는다. 새 테스트 파일이나 서비스 수정은 이번 점검에서 추가하지 않았다.

페이지 로딩 속도·Core Web Vitals·실제 Vercel 비용은 이번 표본으로 수치 평가하지 않았다. HTTP 한 번의 지연을 성능 결함으로 보고하지 않았다. 운영 DB 접속, 대량 크롤링, 배포, 캐시 강제 파기는 수행하지 않았다.
