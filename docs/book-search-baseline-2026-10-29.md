# 도서 검색 개선 기준선 (2026-10-29)

새 테이블이나 검색엔진을 도입하기 전에, 현재 검색의 누락과 순위 문제를 구분한다.
아래 기준선을 측정할 때는 검색 동작·DB 스키마를 변경하지 않았다.
이후 구현과 검증은 [범용 검색 개선](book-search-improvement-2026-10-29.md)에 기록했다(운영 미적용).

## 측정 방법

- 운영 웹의 공개 JavaScript에서 확인한 API에 `GET /book/external/list`를 순차 요청했다.
- 조건은 `display=10`, `start=1`, `sort=sim`, 통합 검색이다. 검색어 기록 API는 호출하지 않았다.
- 고정 검색어 30개와 정상 제목 검색에서 확보한 ISBN 1개를 사용했다.
- 특정 작품은 제목·저자 문자열로 판정한다. 생텍쥐페리/생택쥐페리 같은 표기를 허용한다.
- 다른 검색에서 목표가 실제로 나온 경우에만 검색 누락으로 판정한다. ISBN은 제목 검색의 반환값을 사용한다.
- HTTP 응답시간에는 네트워크·서버·캐시가 섞여 있다. 콜드/웜 상태를 통제하지 않았으므로 DB 성능 수치로 해석하지 않는다.
- 주제 검색 6개와 `그리스 신화`는 수동 평가 대상이다. 결과 수만으로 적합도를 판정하지 않는다.
- 이 표본은 사용자의 실제 검색 분포를 대표하지 않으며, 전체 검색 품질 점수나 Recall@10이 아니다.

운영 DB도 기존 `tools/book-ingest/.env`의 조회용 설정으로 확인했다. `BEGIN READ ONLY`와
`SHOW transaction_read_only = on` 확인 후 SELECT만 실행하고 ROLLBACK했다. 도서는
82,510권이며 인덱스는 ISBN PK와 `IDX_books_search_key_trgm`이다. 현재 코드의
`buildSearchQuery()`로 위 세 제목·저자 검색을 직접 실행해 HTTP 결과와 순서가 같음을 확인했다.
접속 문자열은 산출물에 저장하지 않았다.

재실행 도구: [`evaluate-book-search.cjs`](../apps/server/scripts/evaluate-book-search.cjs).
루트에서 아래 명령을 실행한다. `@bookjeok/core`의 기존 빌드가 필요하다.

```sh
node apps/server/scripts/evaluate-book-search.cjs <API-origin> .tmp/book-search-baseline.json
```

## 첫 개선 대상: 저자·제목 조합의 순위

`한강 채식주의자`와 `채식주의자 한강`은 같은 의도로 볼 수 있지만 원작의 순위가 달라진다.
두 검색의 상위 후보는 다음과 같다.

| ISBN            | 제목                                               | 저자   |
| --------------- | -------------------------------------------------- | ------ |
| `9788965543077` | 한강 채식주의자 다시 읽기 (외설인가 예술인가)      | 양관수 |
| `9788936434595` | 채식주의자 (한강 소설ㅣ2024년 노벨문학상 수상작가) | 한강   |

DB에서 확인한 판매지수는 해설서 54, 원작 141,337이었다. 인기 신호가 부족해서 생긴
역전이 아니라, 판매지수보다 먼저 비교하는 관련도 단계에서 생긴 역전이다.

현재 `KEYWORD_RELEVANCE_ORDER`는 검색어 전체의 제목 접두일치를 제목 내 모든 단어
일치보다 앞에 둔다. 첫 검색은 해설서의 제목 접두일치가 우세하고, 뒤집은 검색은
원작 제목·부제의 접두일치가 우세하다. 따라서 이 사례는 판매지수 조정보다 먼저
저자 필드와 제목 필드의 대응을 반영할 대상이다.

다음 변경에서는 **저자로 식별된 단어와 나머지 제목 단어가 각각 맞는 후보**를
명시적으로 평가한다. 책 제목에 작가 이름이 언급된 해설서와 실제 작가의 원작을 구분한다.
한 단어의 저자 부분일치를 무조건 승격하면 동명이인·다중저자에서 부작용이 생기므로
별도 회귀 사례가 필요하다.
