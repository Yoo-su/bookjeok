## 확인된 비용 요인

### 1. 배포별 캐시 재생성: 정상 동작이지만 비용이 든다

Vercel ISR 캐시는 배포 단위다. 이전 배포 캐시는 롤백용으로 남지만 새 배포에서 재사용하지 않는다. 30일 TTL은 여러 배포를 관통하는 보장이 아니다. 배포만으로 모든 ISBN을 자동 재생성하는 것은 아니며, 새 배포 후 실제 요청받은 경로에서 생성이 발생한다. [Vercel ISR](https://vercel.com/docs/incremental-static-regeneration)

도서 상세의 `revalidate = 2592000`과 `generateStaticParams() => []`는 이미 적용되어 있다. `fetchBookDetail`은 Axios + React `cache()` + 인스턴스별 10분 LRU를 사용한다. 이는 배포 간 공유되는 영속 Data Cache가 아니다. 새 인스턴스에서 상세와 저장된 요약을 가져와 렌더해야 한다. 제목 메타데이터와 본문 조회는 React cache로 묶이므로 무조건 두 번 조회한다고 세지 않는다.

최신 커밋은 `[locale]/layout.tsx`도 언어 목록 대신 빈 배열을 반환하게 변경했다. 기존 ISBN 상세의 온디맨드 생성은 원래 있던 동작이고, 이번 변경은 홈·약관 등 언어별 페이지까지 첫 방문 생성으로 옮긴 것이다. 소수 고정 페이지 변경만으로 대규모 비용 초과를 설명할 수는 없다. 빌드 시 백엔드 접근을 없애려는 결정이므로 원복 전에 그 제약을 해결해야 한다.

### 2. 사이트맵의 응답 캐시 회귀

`apps/web/src/app/sitemap.ts:17`의 `await connection()`이 동적 실행을 강제한다. 최신 커밋에서 라우트의 6시간 `revalidate`를 제거하고 `unstable_cache(buildSitemap)`만 남겼다. **목록 데이터는 6시간 캐시하지만 HTTP 응답은 캐시하지 않아**, 반복 요청마다 함수와 XML 직렬화가 실행된다. 운영에서도 MISS 반복을 확인했다.

개선 방향은 빌드 API 비의존 요구를 유지하면서 XML 응답을 CDN에서 캐시하도록 만드는 것이다. 데이터 캐시만 늘리는 것으로는 해결되지 않는다. 수정 시 공개 글 전체 수집, preview 차단, 장애 시 이전 정상 결과 보존을 함께 검증해야 한다.

측정한 sitemap은 총 192 URL, 그중 책 상세 86개다. 전체 5만여 권을 sitemap에 넣고 있는 상태는 아니다. 검색엔진은 다른 링크나 과거 색인을 통해 더 많은 책을 요청할 수 있다. 현재 sitemap 요청량을 모르므로 이것만 주범이라고 단정하지 않는다.

### 3. 잘못된 하위 경로의 반복 SSR

미들웨어는 첫 세그먼트만 `PATHS` 허용 목록과 비교한다. `/ko/unknown`은 막지만 `/ko/book/not-a-route`는 `book`이 허용되어 통과한다. 이후 `[locale]/[...not_found]`가 큰 레이아웃을 매번 렌더하고 `private, no-store`로 응답한다.

위 URL 두 번으로 144,723 B의 404가 반복 생성됨을 재현했다. 알려진 루트 아래의 임의 경로가 같은 패턴을 만든다. 스캐너가 이 경로군을 많이 때리면 CPU와 Origin Transfer가 함께 증가할 수 있다. 실제 공격량은 미확인이다.

개선 방향은 전체 라우트 형태를 검증하거나 잘못된 경로에 가벼운 404를 제공하는 것이다. 유효 동적 경로와 편집·등록 화면을 막지 않는 회귀 검증이 필요하다. 상위 `dynamicParams = false`는 정상 동적 상세까지 막으므로 사용하지 않는다.

### 4. 모든 페이지의 공통 데이터와 홈 시드 크기

`[locale]/layout.tsx:98`은 전체 번역 메시지를 클라이언트에 전달한다. 운영 HTML 안 RSC를 분석한 결과 홈과 책 상세 모두 한국어 메시지 79,491 B(공백 제거 JSON)가 포함되어 있다. 책 상세 전체 HTML은 약 215KB, 홈은 약 783KB다. 이 값들은 압축 전이다.

홈에는 판매 목록 68,914 B, 인기책 14,435 B, 리뷰 47,152 B, 출판사 서가 30,619 B, 라운지 17,485 B의 쿼리 데이터가 실린다. 모두 불필요하다는 뜻은 아니며 화면별 DTO와 번역 namespace 범위를 검토할 근거다. 리뷰 20건은 5행 티커의 순환 풀이라는 기존 요구가 있으므로 단순히 5건으로 줄이지 않는다.

크기 축소는 캐시 생성·저장·원본 전송 비용을 줄일 수 있지만, 압축 전 크기로 청구 단위를 계산하면 과장된다. 실제 ISR 내부 압축·HTML/RSC 표현별 계량은 대시보드에서 확인해야 한다.

## 비용 지표 해석 시 정정할 점

- ISR Reads/Writes는 방문 횟수가 아니라 **8KB 데이터 단위**다. CDN 계층의 읽기·쓰기는 무료이고 durable ISR 저장소 접근이 과금된다. `x-vercel-cache: HIT`만으로 durable read의 발생 여부나 청구량을 산출할 수 없다. 기존 캐싱 문서의 “HIT에도 무조건 read 과금” 및 과거 쓰기 수/고유 경로 비율로 prefetch를 단정한 설명은 근거가 부족하다. [ISR 과금](https://vercel.com/docs/incremental-static-regeneration/limits-and-pricing)
- Active CPU는 실행 시간이며 외부 API 응답 대기 시간은 제외한다. TTFB가 2초라고 CPU를 2초 쓴 것이 아니다. [Fluid 과금](https://vercel.com/docs/functions/usage-and-pricing)
- Fast Origin Transfer는 사용자에게 전송한 전체 정적 자산 트래픽과 구별된다. 함수·ISR·미들웨어·Blob 경로를 확인해야 한다. 미들웨어에서 차단하면 후속 페이지 렌더는 막지만 미들웨어 자체 사용량까지 항상 0이라는 뜻은 아니다. [CDN 과금](https://vercel.com/docs/manage-cdn-usage)

## 이번에 주원인으로 확인하지 못한 것

- 도서 상세의 지속적인 SSR: 두 정상 ISBN에서 HIT 전환 확인.
- 목록 링크의 무제한 prefetch: 도서 카드·주요 슬라이더·최근 본 책·AI 추천에 `prefetch={false}` 존재. 모든 경로에서 prefetch가 0이라는 뜻은 아니다.
- 도서 LRU의 무제한 증가: 상세 500개, 목록 200개 상한 확인. 전체 프로세스의 메모리 누수 부재를 증명한 것은 아니다.
- 책 표지의 Vercel 이미지 변환 폭증: 주요 도서 표지는 R2 자사 CDN을 사용하고 `unoptimized`가 적용되어 있다. 다른 이미지와 Blob은 별도로 확인해야 한다.
- 주기적 전체 ISBN 갱신: 해당 런타임 루프를 발견하지 못했다. ISR 시간 만료는 전수 순회 cron이 아니다.

## 다음 판별에 필요한 운영 데이터

같은 기간·같은 프로젝트/환경으로 비교한다. 이번 요청의 공개 GET은 과거 사용량과 실제 CPU 프로파일을 대체하지 못한다.

1. 배포 시각과 ISR Writes/Active CPU의 시간별 피크를 겹친다. 배포 직후 여러 정상 ISBN에서 생성이 몰리면 배포별 재생성 가설을 지지한다.
2. Functions를 경로·상태 코드별로 집계한다. `/sitemap.xml`, `[...not_found]`, 정상 책 상세 각각의 호출 수와 Active CPU 합계를 확인한다.
3. ISR을 경로별 Reads/Writes 단위, 고유 경로 수, 재생성 횟수로 구분한다. 단위 수를 실행 횟수로 해석하지 않는다.
4. 요청 로그에서 UA·국가·URL·HTML/RSC·prefetch 비중을 확인한다. UA 문자열은 위장 가능하므로 실제 검색봇 검증 정보도 함께 본다.
5. Fast Origin Transfer의 프로젝트·지역·입출력 및 함수/Blob 비중을 확인한다. 정상 책 상세가 HIT인데 CPU가 계속 높다면 동적 404·미들웨어·다른 함수로 범위를 넓힌다.

우선순위는 **상위 소비 경로 확인 → sitemap 응답 캐시와 잘못된 하위 경로 처리 → 공통 메시지/시드 페이로드 축소 → 배포 횟수·사전 생성 범위 조정**이다. 검색 노출을 일괄 차단하거나 책 ISR을 SSR로 바꾸는 것은 권하지 않는다.
