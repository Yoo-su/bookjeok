# 범용 도서 검색 개선 (2026-10-29)

**운영 DB 인덱스는 2026-11-02 생성·확인했다. 넓은 검색의 비용을 줄이고 운영 READ ONLY에서 결과 동등성을 검증했다. 서버 배포·HTTP·동시 요청 검증은 남아 있다.**
개별 검색어나 시리즈마다 매핑을 추가하지 않고, 기존 서지와 소개를 일반적인 검색 근거로 활용한다.
새 테이블·컬럼·확장·환경 변수·실시간 AI 호출은 추가하지 않는다.

## 구현

1. 원문 제목·저자·출판사 검색과 기존 pg_trgm 표현식 인덱스를 유지한다.
2. 통합 검색에만 별도 확장 경로를 더한다. `책`, `추천`, `다루는` 같은 요청 표현을
   제외하고 일부 명확한 조사를 완화한다. `소설`, `입문`, `어린이` 같은 조건은 남긴다.
   이 규칙은 형태소 분석이나 자연어 이해 모델이 아니며 원문을 대체하지 않는다.
3. PostgreSQL `simple` 전문검색으로 제목·저자·출판사·소개를 검색한다. 핵심 단어들은
   AND로 연결하고 접두어를 허용해 `불안`으로 `불안을`, `윤리`로 `윤리적` 등을 찾는다.
   원문·완화 표기는 같은 단어 안에서 OR로 묶는다.
4. 원문 서지 후보와 전문검색 후보의 ISBN을 UNION으로 합쳐 중복을 제거한다.
   단, 입력 전체가 후보의 저자 이름·출판사와 정확히 일치하면 소개 검색·소개 재정렬을
   생략한다. 이 경우 기존 서지 후보와 판매지수 정렬을 유지한다.
5. 제목·출판사 완전일치를 보존한다. 저자 이름 하나가 정확히 맞고 나머지 단어가 제목에
   맞는 조합을 제목 접두일치보다 앞에 둔다. 괄호 역할 표기와 다중저자 구분자를 처리하며,
   이름 일부만 맞는 작가를 승격하지 않는다.
6. 서지 관련도·판매지수로 고른 상위 200권에만 비싼 소개의 위치·빈도 점수를 계산한다.
   후보나 전체 건수를 200권으로 제한하지 않는다. 이후 페이지도 검색되며 ISBN으로 순서를 고정한다.
7. ISBN 형식은 통합 검색에서 PK 정확 후보를 원문 서지 후보에 UNION으로 합친다.
   숫자가 제목에 포함된 기존 결과도 유지하고, 관련도순에서는 ISBN 정확 일치를 먼저 둔다.
   ISBN 입력은 소개 검색으로 넓히지 않는다.

### 기존 결과 누락 방지 (2026-10-30)

ISBN 입력을 별도 조회 후 바로 반환하던 구현은 같은 숫자가 제목에 든 기존 결과를
제외할 수 있어 위의 UNION 방식으로 보완했다. ISBN이 DB에 없어도 숫자 제목은 계속 찾는다.
일반 검색의 원문 조건은 유지하며 조사·요청 표현 확장과 소개 검색은 후보를 더한다.
추가 후보·순위 변경으로 기존 책이 뒤 페이지로 이동할 수는 있다.

작은 실제 PostgreSQL 테이블에서 13개 입력을 4개 검색 필드, 소개 검색 켜짐/꺼짐,
짧은 단어의 인접 검색 분기로 비교해 원문 검색의 ISBN 집합이 보존되는지 검증했다.
ISBN 후보와 숫자 제목 병합·전체 건수·신간순 및 200권 이후 페이지를 포함해 SQL 12개 테스트를
통과했다. 모든 검색어와 운영 부하에서의 무결함을 보장하는 검증은 아니다.

특정 필드 검색은 해당 필드만 조회한다. `c++`, `C#`, `Q&A`, `%` 같은 기호의 의미를 잃지
않도록 해당 검색은 소개 검색으로 넓히지 않는다. 한 단어의 1~2글자 검색도 과도한 접두어
확장을 막기 위해 소개 검색을 하지 않는다.

### 비용

- 첫 운영 실험에서 소개 전체 ILIKE 검색은 첫 검색 `불안 심리학`이 6초 제한으로 취소됐다.
  따라서 이 쿼리를 운영 검색 경로에 넣지 않았다.
- 로컬에서 모든 후보의 소개 점수를 계산한 `관계 심리`는 약 2.4초,
  `사랑 소설`은 약 3.5~4.3초였다. 200권 재정렬로 바꾼 뒤 각각 약 249~274ms,
  530~559ms였다. 후보 수는 각각 1,966·4,901건으로 유지됐다.
- 200권 재정렬을 적용한 첫 로컬 실험에서 `인공지능 윤리`는 232~244ms, `세계문학전집`은 약 120ms였다.
  원래 매우 빠른 서지 검색에 비해 추가 비용은 존재한다.
- 새 인덱스 크기는 로컬에서 **138,698,752바이트(약 132.3MiB)**였다.
  읽기 전용으로 확인한 운영 DB 크기는 당시 263,343,251바이트(약 251.1MiB)였다.
  실제 운영 인덱스 크기·빌드 시간·최종 가용 용량은 운영에서 확인해야 한다.
- 2026-10-29 17:04 KST 읽기 전용 재확인: 접속 DB는 263,367,827바이트,
  Supabase 공식 DB 보고서 계산 방식인 클러스터 DB 크기 합계는 **278,597,809바이트**였다.
  새 소개 인덱스는 아직 없다. 무료 플랜 500MB를 보수적으로 500,000,000바이트로 잡으면
  현재 약 221.4MB가 남고, 로컬 측정과 같은 크기의 인덱스를 추가하면 약 82.7MB가 남는다.
  이는 실제 프로젝트 요금제 조회나 물리 디스크·WAL 여유 공간 측정은 아니다.
- 로컬 실행 계획에서 소개 후보 조회가 해당 GIN 인덱스를 사용하는 것을 확인했다.
- 이 시간들은 로컬 WASM PostgreSQL 수치다. 운영 성능 향상률이나 운영 지연시간으로
  사용하면 안 된다. 각 2회 측정은 콜드/웜 상태를 엄밀히 통제한 측정도 아니다.

### 속도 보완 검증

확장 검색을 모든 검색에 일괄 적용하면 `민음사` 같은 명확한 출판사 검색에서도 소개를
분석해 비용이 늘었다. 정확한 저자·출판사 일치 경로를 분리했다. 로컬 EXPLAIN ANALYZE에서
`민음사`의 소개 GIN 인덱스 경로가 실제 실행되지 않음(`Actual Loops: 0`)을 확인했다.

원문 조건과 짧은 조사 완화어를 OR로 묶으면 인덱스를 사용하는 원문 조건의 정규화 식까지
전체 스캔할 수 있어, 각 조건을 별도 조회하고 ISBN을 UNION하도록 바꿨다.

## 운영 적용·측정 (2026-11-02)

기존 `IDX_books_search_key_trgm`과 같은 `IDX_books_<대상>_<종류>` 규칙으로
`IDX_books_search_document_gin`을 `CREATE INDEX CONCURRENTLY` 한 문장으로 생성했다.
DDL 외 사전·사후 확인과 검색 측정은 모두 `BEGIN READ ONLY`에서 실행했다.

- 도서 82,511권, 생성 시간 167,946ms(약 2분 48초).
- `indisvalid=true`, `indisready=true`. 인덱스 142,680,064바이트(약 142.7MB/136.1MiB).
- 클러스터 DB 크기 합계: 278,933,681 → 421,613,745바이트.
  500,000,000바이트 가정 시 약 78.4MB 남는다. WAL·물리 디스크 여유와는 구분한다.

## 넓은 검색 최적화·재검증 (2026-11-02)

이번 비교 기준은 소개 검색이 이미 구현된 **`f650a31914e22ccbf891eabafb164dd1b25f00b3`**이다.
위의 `a32cdd31` 대비 기능 확장 측정과 구분한다. 검색 범위·순위 규칙·200권 재정렬 범위는 바꾸지 않았다.

- 후보 수집 시 제목·저자·출판사·판매지수·출간일도 가져와 후보별 PK 재조회를 없앴다.
  소개 후보 중 서지 후보에 없는 ISBN만 `UNION ALL`로 더한다. PK가 유일하므로 기존 UNION과
  후보 집합은 같고, 전체 후보의 중복 제거 정렬은 필요하지 않다. 소개 본문은 후보 CTE에 싣지 않는다.
- 관련도 CASE를 한 번 계산해 ISBN·판매지수·관련도 정수만 담은 CTE를
  200권 선정과 최종 정렬에서 재사용한다. 정규화 문자열을 창 함수까지 운반하지 않는다.
- 짧은 토큰의 원문이 한글(`Script=Hangul`)·ASCII 숫자로만 이루어졌으면 `LIKE`를 쓴다.
  대소문자가 없는 문자이므로 의미를 유지하면서 ILIKE의 행 전체 소문자 변환 비용을 줄인다.
  영문·다른 문자·기호는 기존 `ILIKE`와 이스케이프를 유지한다. 짧은 검색의 전체 스캔 자체는 남는다.
  ILIKE의 로케일별 대소문자 비교는 [PostgreSQL 문서](https://www.postgresql.org/docs/17/functions-matching.html),
  다중 바이트 문자열의 소문자 변환은 [PostgreSQL 17 소스](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/adt/like.c)를 확인했다.

먼저 현행 SQL을 다시 실행해 `이야기`의 3초 제한 초과를 재현했다. 후보 서지 재사용만 적용했을 때
반복 실행은 약 826ms → 608~610ms였고, 관련도 재사용 후 약 589ms였다.
이는 서로 다른 실험이며 캐시를 통제하지 않아 단계별 개선률로 합산하지 않는다.
`사랑 소설`의 짧은 단어 ILIKE 전체 스캔은 이전 구현에도 있었고, 이번 확장이 새로 만든 스캔이 아니다.

최종 SQL은 같은 운영 연결에서 16조건×수정 전후 각 3회, 순서를 교대로 비교했다.
각 비교는 `REPEATABLE READ READ ONLY`의 동일 스냅샷을 사용했고, 쿼리당 3초·실행 간 200ms로 제한했다.
아래는 **검색·정렬·건수 단일 SQL의 클라이언트 왕복 시간**이며 사전 조회·상세·HTTP 시간은 제외한다.
첫 실행과 2·3회차를 구분하지만, 어느 쪽도 실제 콜드/웜 캐시를 통제한 측정은 아니다.

| 검색어 | 수정 전 첫 회 ms | 수정 후 첫 회 ms | 수정 전 2·3회차 ms | 수정 후 2·3회차 ms |
| --- | ---: | ---: | ---: | ---: |
| 사랑 소설 | 3초 제한 취소 | 1,743.3 | 690.0~742.6 | 244.1~286.7 |
| 이야기 | 974.7 | 611.7 | 838.9~866.1 | 604.9~657.8 |
| 민음사 | 300.1 | 29.7 | 36.0~38.0 | 29.8 |
| 인공지능 윤리 | 756.1 | 181.8 | 186.4~197.2 | 180.9~197.4 |
| 기후 위기 (신간순) | 45.6 | 13.7 | 18.7~19.4 | 13.2~13.7 |

수정 후 48회는 모두 완료했고, 수정 전은 1회가 3초 제한으로 취소됐다.
양쪽이 완료된 47쌍의 첫 페이지 ISBN·순서·전체 건수는 모두 같았다.
EXPLAIN ANALYZE에서 `이야기`의 후보 31,299건 PK 재조회는 사라졌고,
소개 재정렬을 위한 200건의 PK 조회만 남았다. 해당 실행의 shared hit blocks는
138,911 → 13,707, temp read/write blocks는 1,169/894 → 276/715였다.
이는 블록 접근 횟수이며 고유 데이터 크기나 캐시 적중률이 아니다. 기존 GIN은 계속 사용한다.

별도 동등성 검증에서는 **16조건 모두 전체 ISBN 순서·건수가 일치**했다.
각 조건의 OFFSET 0·195·200·마지막 5건·범위 밖 페이지와 별도 COUNT도 동일 스냅샷에서 비교했다.
`이야기` 31,299건, `사랑 소설` 4,902건을 포함해 후보를 자르지 않았다.
이 검증은 기존 SQL이 3초 제한에 걸려 **검증 연결만 8초**로 늘려 완료했다.
성능 측정은 계속 3초이며 서버 런타임에 시간 제한·자동 폴백을 추가한 것은 아니다.

관련 Jest 4스위트·50개, 실제 PostgreSQL SQL 13개(짧은 한글·숫자·영문·기호의 원문 ILIKE와
4개 필드 동등성 포함), 서버 타입 검사·변경 파일 ESLint가 통과했다.
원본은 비추적 `.tmp/book-search-optimization-caseless-like.json`,
`.tmp/book-search-optimization-full-result-equivalence.json`이며 중간 실험도 같은 접두어로 남겼다.
동일 비교는 로컬 `.tmp/optimize-book-search.cjs`의 `--full` 및 `--full --verify`로 재실행한다.
접속 문자열·사용자 데이터는 산출물에 없다. **새 DDL·인덱스·운영 데이터 쓰기·배포는 수행하지 않았다.**
HTTP·동시 요청 및 통제된 콜드 캐시 성능은 검증하지 않았으며, 모든 입력의 성능을 보장하지 않는다.

## 적용 순서

검증은 서버 전체 61개 스위트·595개 테스트, 별도 PostgreSQL SQL 시나리오 10개,
서버 타입 검사·변경 파일 ESLint·Nest 빌드가 통과했다. 실행 환경은 Node 24.15.0이며,
저장소가 지정한 Node 22 환경과 실제 배포 서버의 통합 검증은 별도로 남아 있다.
속도 보완 이후에는 관련 4개 스위트·50개 테스트와 타입 검사·린트를 다시 통과했다.

1. 현재 DB 가용 용량과 추가 인덱스 크기를 확인한다. **2026-11-02 확인 완료.**
2. [`인덱스 SQL`](ddl/2026-10-29-book-discovery-index.sql)의 CREATE 문만 단독 실행한다.
   `CONCURRENTLY`이므로 BEGIN/COMMIT으로 감싸거나 다른 문장과 한 요청으로 실행하지 않는다.
3. 별도의 SELECT로 `indisvalid`·`indisready`와 실제 크기를 확인한다. **2~3단계는 2026-11-02 완료, CREATE를 재실행하지 않는다.** 실패한 인덱스를
   이름만 보고 재사용하지 않는다.
4. 넓은 검색의 운영 READ ONLY 최적화·동등성 검증은 완료했다. 별도 배포 작업에서 서버 코드를 배포·재시작한다. 시작 시 인덱스가 유효한 경우에만 소개 검색이 켜진다.
   인덱스가 없으면 원문 서지 검색·조사/요청 표현 확장·순위 개선·ISBN 검색만 사용한다.
   나중에 인덱스를 만들었다면 서버를 다시 시작해야 한다.
5. 운영 HTTP 평가와 실제 쿼리 계획·지연시간을 다시 확인하고 DDL 적용 이력을 기록한다.

되돌릴 때는 **소개 검색을 사용하지 않는 서버 버전으로 먼저 되돌린 후** 인덱스를 제거한다.
인덱스를 사용 중인 서버를 그대로 둔 채 제거하면 전체 소개 스캔이 발생할 수 있다.

## 남는 한계

- 단어 근거가 없는 의미 연결과 동의어·약칭 이해, 오타 교정은 구현하지 않았다.
- `simple`은 한국어 형태소 분석기가 아니다. 조사 완화와 접두어가 일부 표기 차이를
  회수하지만 합성어 내부의 단어나 모든 활용형을 처리하지는 못한다.
- 소개에 언급된 장르·시리즈가 실제 소속을 보장하지 않는다. 예를 들어 소설가가 쓴 에세이가
  `소설`을 언급하면 후보가 될 수 있다. 시리즈 소속·장르 필터로 표현하지 않는다.
- 세계문학전집의 낱권을 추가로 찾더라도 제목이 정확히 맞는 세트보다 모두 먼저 나오는 것은 아니다.
- 소개 점수는 상위 200권에만 반영된다. 나머지는 서지 관련도·판매지수 순이며,
  오래된 판매지수에 따른 인기 편향은 남는다.
- 실제 검색어와 사용자 평가를 확보해 상위 결과의 적합도·누락을 계속 평가해야 한다.
