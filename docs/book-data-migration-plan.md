## 1. 배경

도서 데이터 공급처가 2년 사이 두 번 끊겼습니다.

- 네이버 책 검색 API 종료 → 알라딘으로 이전
- 알라딘 Open API 종료 → **현재 대응 중**

이제 사기업 API를 런타임 경로에 두지 않는 구조로 바꿉니다. 카카오로 갈아타는
것은 같은 사고를 세 번째로 반복하는 것이므로 주 공급처로 쓰지 않습니다.

공지에서 확인한 사실:

- 기존 수신 데이터 재사용 가능 여부에 대한 언급도 없음

### 핵심 판단

알라딘은 성격이 다른 세 가지 역할을 겸하고 있고, 각각 답이 다릅니다.

| 역할                 | 현재                                   | 위험도 | 대응                                       |
| -------------------- | -------------------------------------- | ------ | ------------------------------------------ |
| ① 표지 이미지 CDN    | `books.image` = 알라딘 URL (약 6만 행) | 치명적 | 자체 호스팅 (대안 없음) — **Phase 0 완료** |
| ② 서지 데이터 소스   | `resolveBook()` 신규 ISBN 유입         | 낮음   | **미정** (아래 6장)                        |
| ③ 실시간 검색 백엔드 | `/book/external/list`                  | 중간   | **미정** (아래 6장)                        |

②는 이미 6만 건이 DB에 스냅샷으로 적재돼 있어 알라딘이 죽어도 기존 도서는
멀쩡합니다. 아픈 곳은 신규 ISBN 유입 경로 하나뿐입니다.

①에는 "다른 API로 교체"라는 선택지가 없습니다. 카카오로 가면 `img1.kakaocdn.net`에,
정보나루로 가면 또 다른 남의 도메인에 6만 행을 묶는 것이라 문제가 그대로
반복됩니다.

### 데드라인의 성격 구분 (중요)

| 구분                | 해당                     | 놓쳤을 때                                                                  |
| ------------------- | ------------------------ | -------------------------------------------------------------------------- |
| **비가역 데드라인** | Phase 0 (표지 원본 확보) | **영구 손실.** cover500 화질 국내 도서 표지 6만 장을 다시 구할 방법이 없음 |
| 가역 데드라인       | Phase 1, 2               | 장애는 나지만 원본만 있으면 몇 시간 내 복구 가능                           |

그래서 **Phase 0이 무조건 최우선**입니다. Phase 0만 끝나면 나머지는 사고가
나도 되돌릴 수 있습니다.

## 2. 확정된 결정

논의로 이미 정해진 사항입니다. 다시 논쟁하지 마세요.

1. **표지는 자체 호스팅한다.** 다른 사기업 CDN으로 갈아타지 않는다.
2. **DB에는 벤더 도메인 URL을 저장하지 않는다.** `books.image`에는 항상 자사
   도메인 URL을 넣고, 실제 스토리지는 그 뒤에서 교체 가능하게 둔다.
   이번 사고의 근본 원인이 "남의 도메인이 6만 행에 문자열로 박혀 있던 것"이다.
3. **외부 도서 API 호출은 서버로 일원화한다.** (2026-09-05 완료 — 웹의 직접
   호출 2곳 제거)
4. **공급처는 포트 뒤에 둔다.** 컨트롤러·서비스는 `BookCatalogProvider`에만
   의존하고, 체인 등록은 `book.module.ts` 한 곳에서만 한다. 다음에 또 끊겨도
   어댑터 하나만 갈아끼우면 되게 한다.
5. **검색과 상세는 체인을 따로 둔다.** 같은 공급처라도 경로에 따라 유불리가
   반대다. 근거는 `book.module.ts`의 등록부 주석에 있다.
6. **카카오를 쓰더라도 주 공급처로는 쓰지 않는다.** 단독 의존 금지.
7. **표지 원본 확보와 DB 컷오버를 분리한다.** 원본만 먼저 확보해 두고
   가공·도메인·컷오버는 시간을 두고 결정한다.

### 알라딘으로 나가는 문 — 3개

모든 호출이 `BookCatalogService` 한 곳을 거칩니다.

| 진입점                      | 위치                 | 체인                            |
| --------------------------- | -------------------- | ------------------------------- |
| `GET /book/external/list`   | `book.controller.ts` | 검색 체인 — **알라딘 우선**     |

실패**하므로 검색 품질 저하보다 심각도가 높습니다.

**1. `cover200` 15,293건(26%)을 DB 값 그대로 받으면 안 된다.**

### 검색·상세 체인 분리 (2026-09-07)

하나의 공급처 배열을 검색과 상세가 공유하고 있었습니다. 그런데 **경로에 따라
자체 DB의 유불리가 정반대**라 한쪽은 반드시 손해를 봅니다.

**분리 당시(인덱스 적용 전)의 판단은 이랬습니다.**

|      | 자체 DB 쿼리               | 인덱스 | 결론                                                                                                                              |
| ---- | -------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 검색 | `title/author ILIKE '%q%'` | 없음   | 5만 행 풀스캔. 게다가 체인은 결과가 한 건이라도 나오면 멈추므로 자체 DB를 앞에 두면 **신간이 검색에서 사라짐** → 알라딘 우선 유지 |
| 상세 | `findOneBy({ isbn })`      | **PK** | 인덱스 단건 → **자체 DB 우선**                                                                                                    |

> **같은 날 이후 근거가 하나 사라졌습니다.** pg_trgm GIN 인덱스를 적용해(8장)
> 검색의 풀스캔 문제는 해결됐습니다. **검색 체인이 아직 알라딘 우선인 이유는
> 이제 성능이 아니라 "자체 DB에 신간이 없다" 하나뿐입니다.** 신간 미러링
> 스케줄러가 그 전제를 만들며, 순서 전환은 그것과 함께 배포됩니다(6-d).

상세를 자체 DB 우선으로 돌린 이유가 하나 더 있습니다. 상세 페이지에 들어오면
`POST /book/:isbn/view`가 `BookResolvePipe`를 태워 그 책을 `books`에 적재합니다.
즉 외부를 먼저 부르면 **방금 우리가 저장한 책을 외부에 다시 물어보는** 꼴이었고,
HTTP 왕복만큼 상세가 느렸습니다.

토큰은 `BOOK_SEARCH_PROVIDERS`·`BOOK_DETAIL_PROVIDERS` 둘이며, 순서는 여전히
`book.module.ts` 한 곳에서만 정합니다.

**감수한 것:** 자체 DB에는 `link` 컬럼이 없어 상세의 알라딘 구매 버튼이 나오지
않습니다. 어차피 종료와 함께 사라질 값이라 앞당겨 받아들였습니다. 그리고 DB에
저장된 옛 `description`이 그대로 노출되므로 **HTML 엔티티 잔류분(6-c)이 화면에
보입니다.** 6-c의 DB 정리가 이제 화면에 직접 영향을 주는 과제가 되었습니다.

### 장애와 "책 없음"을 구분하지 못하던 결함 (2026-09-07 수정)

`BookCatalogService.runChain()`에 "공급처가 전부 죽었을 때만 예외를 전파한다"는
보호장치가 있었는데, **자체 DB 어댑터가 체인에 들어간 시점부터 무력화돼
있었습니다.**

자체 DB는 못 찾아도 `null`을 정상 반환할 뿐 예외를 던지지 않습니다. 그래서
`anyResponded`가 **항상** true가 되었고, 외부 공급처가 전부 죽어도 예외 대신 빈
결과가 나갔습니다. 그러면 상세 페이지가 `notFound()`를 띄우고 **그 404가 ISR
캐시에 24시간 고착**됩니다. 주석이 막으려던 바로 그 일입니다.

알라딘 장애 때 이미 발생할 수 있었고, 2026-10-30에는 확정적으로 터질 상태였습니다.

**수정:** 포트에 `kind: 'external' | 'local'`을 추가하고, 빈 결과의 판정 자격을
외부 공급처에만 부여했습니다. 자체 DB의 "못 찾음"은 "그런 책이 없다"가 아니라
"우리가 아직 안 가졌다"이기 때문입니다. 외부 공급처가 하나도 없는 구성(알라딘
제거 후)에서는 자체 DB가 그 자격을 대신합니다.

회귀 방지 테스트 5건을 `book-catalog.service.spec.ts`에 고정했습니다.

### 국립중앙도서관 — 검토했으나 채택하지 않음 (2026-09-07)

**결정 완료. 다시 논쟁하지 마세요.**

계획 수립 당시 ②③의 답으로 국중 ISBN 서지정보 API를 지목했으나, 구현 착수 전에
철회했습니다. 사유:

1. **서지 상세정보 결측이 많다.** 책소개·목차 등이 비어 있는 레코드 비율이

## 6-b. 공급처 전환 전 사전 점검 결과 (2026-09-06)

알라딘 말고 다른 공급처로 바꿨을 때 터질 곳을 코드에서 훑은 결과입니다.
**공급처가 무엇이든 해당되는 내용**이라 국중 폐기 후에도 그대로 유효합니다.

### 처리 완료

**NOT NULL 컬럼 폴백 부재** — `books`는 `title`·`author`·`publisher`·
`description`·`image`가 전부 NOT NULL인데, `resolveBook()`이 `title`·`author`·
`publisher`에 폴백 없이 공급처 값을 그대로 넣고 있었습니다. 알라딘은 늘 채워
주지만 공공 서지에는 저자 표기가 없는 자료가 실제로 있어, 그대로면 INSERT 실패
→ 판매글·리뷰 등록이 막힙니다.

- 저자·발행처가 비면 빈 문자열로 채웁니다.
- **제목이 없으면 저장하지 않고 `BOOK_NOT_FOUND`를 던집니다.** 식별 불가능한
  레코드를 넣어봐야 목록에 빈칸으로만 보입니다.
- 두 경우 모두 `book.service.spec.ts`에 테스트로 고정했습니다.

### 새 공급처를 붙이면 가장 먼저 확인할 것

**`BookResolvePipe` 실패 = 등록 실패.** 파이프가 판매글 생성·리뷰 작성·위시리스트
추가 앞단에 붙어 있어, 공급처가 책을 못 찾으면 등록 자체가 실패합니다. 검색 품질
저하보다 이쪽이 훨씬 치명적입니다.

→ 커버리지 실측은 인기 도서가 아니라 **최근 등록된 판매글의 ISBN**으로 하세요.
실사용 분포에 가깝습니다. 여기서 통과하지 못하면 그 공급처 단독으로는 갈 수 없습니다.

**표지 URL을 그대로 DB에 저장** — `resolveBook()`의 `image: bookData.image`가
그 지점입니다. 공급처를 바꾸면 그 공급처의 URL이 하루 100건씩 쌓입니다(7-b 참조).

## 6-c. HTML 엔티티 잔류 (2026-09-06)

책 상세의 소개 글에 `&#8231;` 같은 코드가 그대로 보이는 문제입니다.
`cleanHtmlText`가 이름 있는 엔티티 7개와 `&#39;`만 처리하고 나머지 숫자 엔티티를
그대로 흘려보내고 있었습니다.

### 운영 DB 실측

| 대상                             | 건수  |
| -------------------------------- | ----- |
| `description`에 숫자 엔티티 잔류 | 303행 |
| `description`에 이름 엔티티 잔류 | 268행 |
| `title`                          | 26행  |
| `author`                         | 1행   |

가장 많이 남은 것은 뜻밖에도 `&gt;`(527회)와 `&lt;`(519회)였습니다. **함수가
이미 처리하는 엔티티인데도 남은 이유는 두 가지입니다.**

1. **디코딩 순서** — `&amp;`를 `&lt;`보다 먼저 풀고 있었습니다. 그래서
   `&amp;lt;`가 `&lt;`가 된 뒤 다시 풀리지 않았습니다.
2. **이중 인코딩** — 공급처가 `<책제목>`을 두 번 인코딩해 보내는 경우가 있습니다.
   국내 도서 소개는 `<제목>` 표기를 자주 써서 이 패턴이 많습니다.

### 수정 내용 (완료)

- 10진(`&#NNN;`)·16진(`&#xHH;`) 숫자 엔티티 디코딩 추가
- 이름 있는 엔티티를 7개에서 21개로 확대(`&middot;` `&hellip;` `&rsquo;` 등)
- **`&amp;`를 마지막에 처리**해 순서 문제 해결
- 값이 안정될 때까지 최대 3회 반복 디코딩(이중 인코딩 대응)
- 모르는 엔티티와 범위를 벗어난 코드포인트는 원문 유지
- 태그 제거를 디코딩보다 먼저 수행하는 순서는 유지 — 디코딩으로 생긴 `<개미>`가
  태그로 오인돼 지워지면 안 됩니다

`apps/web/src/shared/utils/__tests__/clean-html-text.test.ts`에 12건으로 고정했습니다.

> 소개 글은 React가 `{description}`으로 이스케이프해 렌더하므로(`dangerouslySetInnerHTML`
> 미사용) 디코딩을 강화해도 XSS 위험은 없습니다.

### 남은 일 — DB 정리

책 상세는 요청 시점에 공급처 응답을 정제하므로 **수정 즉시 정상화됩니다.**
그러나 `books`에 이미 저장된 값은 옛 정제 결과라 엔티티가 남아 있습니다. AI 검색
결과 등 DB에서 직접 읽는 경로에는 계속 보입니다.

- [ ] `books`의 `description`·`title`·`author`에 잔류한 엔티티 일괄 정리
      (약 600행. 전체의 1% 미만이라 급하지 않으며, Phase 2 컷오버 때 같은 배치에
      묶는 편이 효율적입니다)

## 6-d. 카카오 도입안 (D9 유력안 · 2026-09-07 검토)

국중을 폐기하면서 비게 된 ②③의 자리를 채우는 안입니다. **아직 결정된 것이
아니라 검토를 마친 유력안입니다.** 사용자가 제안한 구조이며, 타당성 검토 결과
문제없다고 판단했습니다.

### 설계

```
새 ISBN → 카카오 책 API 조회 (서지 + 표지 URL)
       → books insert
       → [배치] 표지 다운로드 → R2 업로드 → books.image를 자사 URL로 교체
```

**핵심은 카카오를 공급처가 아니라 유입구로만 쓴다는 점입니다.** 들어온 데이터는
즉시 자산으로 전환하므로, 카카오가 언젠가 종료해도 그때까지 확보한 것은 전부
남습니다. 네이버·알라딘 때 아팠던 이유는 벤더가 죽으면서 데이터까지 같이 죽었기
때문인데, 이 구조는 그 연결을 끊습니다.

「확정된 결정」 6번(카카오를 주 공급처로 쓰지 않는다)과도 충돌하지 않습니다.
카카오는 파이프의 입구일 뿐 서비스가 의존하는 공급처가 아닙니다.

### 구현 기반은 대부분 갖춰져 있습니다

| 필요             | 현재                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| 스케줄러         | `@nestjs/schedule` 설치·등록됨. `order-scheduler.service.ts`에 `@Cron` 선례 6개                           |
| 이벤트 리스너    | `@nestjs/event-emitter`. 리스너 10개 선례                                                                 |
| 공급처 포트      | `BookCatalogProvider`. 어댑터 하나 추가하면 끝                                                            |
| 스토리지 업로드  | `@vercel/blob`만 있음. **R2는 `@aws-sdk/client-s3` 추가 필요**                                            |
| `remotePatterns` | `img1/k.kakaocdn.net`은 있으나 **로그인 프로필용**. 책 썸네일은 `search1.kakaocdn.net`이라 별도 추가 필요 |

### 설계 보정 세 가지

**① 배치 트리거는 개수가 아니라 조건 쿼리로.**
"신규 100건이 쌓이면"은 배치가 한 번 실패하면 그 100건이 영영 처리되지 않습니다.
시간 기반 크론이 "아직 자사 도메인이 아닌 도서 100건"을 집어가게 하세요.
카운터가 필요 없고, 실패분이 다음 회차에 자동으로 다시 잡힙니다.

**② 벤더 URL을 `books.image`에 넣지 않는 편이 낫습니다.**
"카카오 URL 저장 후 교체"는 지금 알라딘에서 겪는 문제를 소규모로 재현합니다.

| 안         | 방식                                                             | 대가                                                 |
| ---------- | ---------------------------------------------------------------- | ---------------------------------------------------- |
| ⓐ 최소     | 카카오 URL 임시 저장 → LIKE로 찾아 교체                          | DDL 불필요. 벤더 URL 노출 창이 존재                  |
| **ⓑ 권장** | `image`엔 플레이스홀더, 벤더 URL은 **`imageSourceUrl`**(미결 D6) | 「확정된 결정」 2번을 문자 그대로 지킴. DDL 1회 필요 |

### 검색 경로 설계 (2026-09-07 결정)

"DB에 없으면 카카오"는 **ISBN 단건 조회에서만 성립합니다.**

| 경로                | 유무 판단                                                                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resolveBook(isbn)` | 가능. ISBN이 PK라 명확합니다                                                                                                                       |
| 키워드 검색         | **불가능.** "데미안"을 검색했을 때 DB에 민음사판이 있다고 해서 사용자가 찾는 열린책들판이 있는 것이 아닙니다. 개수로도 유무로도 판단할 수 없습니다 |

두 안을 검토했습니다.

| 안                                   | 방식                                                                                           | 문제                                                                                                |
| ------------------------------------ | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 실시간 병합                          | 검색마다 자체 DB와 카카오를 병렬 호출해 ISBN으로 dedupe                                        | 매 검색이 벤더를 탑니다(1장 목표와 충돌). 소스별 오프셋이 달라 무한 스크롤에서 중복·누락이 생깁니다 |
| **채택: 스케줄러 미러링 + 0건 폴백** | 스케줄러가 신간을 미리 `books`에 적재. 검색은 자체 DB만 보고, **0건일 때만** 카카오를 1회 조회 | 미러링 완전성을 보장할 수 없습니다. 폴백이 그 구멍을 메웁니다                                       |

```
검색 → 자체 DB
        ├─ 결과 있음 → 그대로 반환 (카카오 호출 없음)
        └─ 0건      → 카카오 1회 조회 → 반환 + books에 적재
```

#### 채택 이유

- **평상시 검색 경로에 벤더가 없습니다.** 1장의 "사기업 API를 런타임 경로에 두지
  않는다"를 지키는 유일한 안입니다.
- 0건은 드물어 카카오 호출이 거의 발생하지 않습니다. 쿼터와 지연 문제가 사라집니다.
- 0건이었던 검색어가 곧 "우리에게 없던 책"이므로, 폴백이 미러링의 구멍을 자동으로
  메웁니다.
- 동일 제목 다른 판본 문제가 사라집니다. 스케줄러가 판본을 함께 당겨오므로 검색
  시점에 이미 DB에 있습니다.
- 병합·페이지네이션 문제가 없습니다.

`runChain`이 이미 "앞선 공급처가 결과를 못 주면 다음"이라, **체인을
`[자체DB, 카카오]` 순서로 등록하기만 하면 오케스트레이터 변경 없이 이 동작이
나옵니다.** book.module.ts 한 줄입니다.

> 검색 체인에서 자체 DB를 앞에 두면 신간이 사라진다는 우려(6장 「검색·상세 체인
> 분리」)는 스케줄러가 신간을 채워주는 전제에서는 성립하지 않습니다. 다만 **그
> 전제가 성립하기 전에 순서를 바꾸면 안 됩니다.** 스케줄러와 0건 폴백이 함께
> 배포되어야 합니다.

#### 스케줄러가 무엇을 당겨올 것인가 (미결)

**카카오는 신간 목록을 주지 않습니다.** 검색 API라 `query`가 필수이며, 국중처럼
발행예정일 순으로 훑는 방법이 없습니다.

현실적인 방법은 **자체 DB의 출판사 목록을 쿼리 사전으로 쓰는 것**입니다.
`target=publisher`와 `sort=latest`로 출판사별 최신순을 주기적으로 훑습니다.
사전은 이미 우리가 갖고 있습니다.

```sql
SELECT COUNT(DISTINCT publisher) FROM books;
```

이 값이 순회 규모와 주기·쿼터 설계를 정합니다. **아직 재보지 않았습니다.**

남는 구멍 세 가지입니다.

- 새로 생긴 출판사는 사전에 없어 놓칩니다
- 스케줄러 주기만큼 지연됩니다
- 쿼리당 페이지 상한이 있어 대형 출판사는 전부 훑지 못합니다

이 구멍들이 검색에서는 불편이지만 **등록에서는 장애**입니다. 그래서 0건 폴백은
선택이 아니라 필수입니다.

#### 책 선택 모달이 특히 중요합니다

판매글·리뷰·독서기록 등록의 입구입니다. 여기서 사용자가 가진 판본을 찾지 못하면
**있는 것을 고릅니다.** 열린책들판을 가졌는데 민음사판으로 판매글이 올라갑니다.

검색 페이지에서 신간이 안 보이는 것은 불편이지만, 이쪽은 잘못된 데이터가 쌓이는
문제라 성격이 다릅니다. 0건 폴백이 여기서 반드시 동작해야 합니다.

### 감수할 것 — 커버리지는 기술로 풀리지 않습니다

검색 속도와 랭킹을 아무리 개선해도 **DB에 없는 책은 나오지 않습니다.**
알라딘·네이버 검색이 좋아 보였던 이유의 절반은 전체 카탈로그를 갖고 있었기
때문입니다. 이건 공급처로만 풉니다.

그래서 D9에는 세 갈래가 있습니다.

| ----- | -------------------------------------------------------------------------------------------------- | -------------------------------------------- |

| ⓑ     | **사용자 직접 등록 경로** — 검색 결과가 없을 때 ISBN 직접 입력 + 제목·저자 입력 + 표지 촬영 업로드 | 벤더 의존 0. 개발 필요, 데이터 품질 편차     |

등록 경로만 뚫으면 커버리지 문제가 장애에서 불편으로 내려갑니다. 중고 거래

### 왜 급한가 — 실측 (2026-09-05)

| 구간      | 신규 도서                   |
| --------- | --------------------------- |
| 최근 7일  | **830건** (하루 약 118건)   |

벌크 적재를 빼도 **하루 100건 이상** 유입됩니다. 1년이면 약 4만 건으로 현재
DB의 70% 규모입니다.

### 유입 경로 규명 (2026-09-07)

이 유입의 정체는 사용자가 아니라 **검색 크롤러입니다.** 경로를 코드에서 특정했습니다.

```
도서 상세 페이지
  └─ 연관 도서 섹션(related-books-section)  ← 알라딘 검색 결과 10개
       └─ BookCard가 /book/{isbn}/detail 로 링크 (book-card.tsx)
            └─ 그 상세 페이지에도 다시 연관 도서 10개
                 └─ …
```

상세 페이지 하나가 **우리 DB에 없는 도서 10개로 가는 링크**를 만들고, 그것이
재귀합니다. 홈 출판사 슬라이더도 18개씩 같은 일을 합니다. 사실상 무한 크롤
공간입니다.

행이 실제로 생기는 지점은 SSR이 아니라 `use-book-view.ts`의 `recordBookView`
POST입니다. 이것이 `BookResolvePipe`를 타면서 `books`에 INSERT합니다. 따라서
**JS를 실행하는 크롤러(주로 Googlebot)만** 행을 만듭니다.

함의 세 가지입니다.

1. **표지 델타가 계속 생깁니다.** Phase 0 체크리스트의 델타 재수집 항목이
   이 때문입니다.
2. **10/30이 지나면 이 유입은 저절로 멈춥니다.** 알라딘이 죽으면 `resolveBook`이
   신규 도서를 만들지 못합니다.
3. **뒤집어 보면 기회입니다.** 지금 크롤러가 알라딘 카탈로그를 우리 DB로 무료로
   옮겨 주고 있습니다. 종료 전에 카탈로그를 최대한 확보해 두면 D9의 크기가
   줄어듭니다(아래 6-d의 "감수할 것" 참조). 10/30이 지나면 이 기회는 사라집니다.

봇 조회는 `books.viewCount`에도 쌓이지만, IP 기반 24시간 중복 방지가 있고
조회수 가중치가 1(독서기록 10·위시리스트 8·리뷰 5)이라 인기 도서 순위를 뒤집을
정도는 아닙니다.

### 문제

현재 `resolveBook()`은 공급처가 준 표지 URL을 그대로 `books.image`에 넣습니다.
이 흐름이 남으면 **새 공급처의 URL이 하루 100건씩 쌓입니다.** Phase 2에서 기존
6만 건을 자체 도메인으로 바꿔놔도 구멍이 계속 새는 셈이고, 그 공급처가 언젠가
바뀌면 지금 겪는 일을 처음부터 다시 겪습니다.

「확정된 결정」 2번(**DB에는 자체 도메인 URL만**)은 일회성 마이그레이션 규칙이
아니라 **상시 규칙**이어야 합니다.

### 설계

```
새 ISBN → 공급처 조회 (서지 + 표지 URL)
       → books insert (image = 플레이스홀더)
       → [비동기 이벤트] 표지 다운로드 → 자체 스토리지 → books.image 갱신
```

비동기여야 하는 이유: `resolveBook()`은 판매글·리뷰 작성이 타는 경로입니다.
여기서 외부 이미지 서버를 동기로 기다리면 등록이 느려지고, 그 서버가 죽으면
등록 자체가 실패합니다.

레포에 이미 `@nestjs/event-emitter` 기반 리스너 패턴이 있습니다
(`order`·`trade`·`chat`·`llm`). 같은 방식으로 붙입니다.

### 체크리스트

- [ ] 표지 수집 이벤트/리스너 추가 (`book.cover_needed` 등)
- [ ] `resolveBook()`에서 신규 도서 생성 시 이벤트 발행
- [ ] 표지 확보 실패 시 재시도 정책 (영구 실패는 플레이스홀더로 확정)
- [ ] 플레이스홀더 이미지 준비 — 기존 `noimg` 471건도 같은 것으로 통일
- [ ] Phase 2의 일회성 수집 코드와 로직 공유 (URL → 스토리지 → DB 갱신)

### 감수할 손실

알라딘 `cover500`은 종료 후 얻을 수 없습니다. **새 공급처가 주는 표지 화질이 곧
신규 도서 표지의 상한**이 되며, 그 화질은 공급처를 정한 뒤에야 측정할 수 있습니다.

기존 56,656건은 고화질로 확보했으므로 **서비스의 대부분은 안전하고, 신규 유입분만
화질이 떨어질 수 있습니다.** 표지 화질은 D9(공급처 선정)의 평가 항목에
반드시 포함하세요.

## 7-c. 스토리지 결정 근거 — 과거 Cloudinary 사고 (D1)

**이 항목은 반복하면 안 되는 실패의 기록입니다.**

### 무슨 일이 있었나

네이버 API가 종료됐을 때 표지 전량을 Cloudinary에 올렸다가 **무료 티어를 초과해
계정이 잠겼습니다.** 용량 문제가 아니었습니다.

Cloudinary는 크레딧 기반이며(무료 25 크레딧/월, 1 크레딧 = 1,000 transformations
또는 1GB 저장 또는 1GB 대역폭), 공식 문서상 **"원본을 업로드하는 것" 자체가
transformation으로 계수됩니다.**

```
56,656건 업로드 = 56,656 transformations ≈ 57 크레딧
월 한도 25 크레딧의 2배 이상 — 저장 용량을 세기도 전에 초과
```

**이미지 처리 서비스를 스토리지로 쓴 것이 원인입니다.** 저장은 부수적이고 과금의
본체는 처리 횟수였습니다.

### 남은 피해

계정이 잠긴 채로 남아 있어 그때 올린 표지가 **현재 운영에서 401로 깨져 있습니다.**
아래 7-d 참조.

### R2에서 같은 일이 생기지 않는 이유

| 항목               | Cloudinary 무료            | R2 무료                        |
| ------------------ | -------------------------- | ------------------------------ |
| 업로드 56,656건    | **57 크레딧** (한도 25) ❌ | Class A 5.7만 (한도 **100만**) |
| 저장 2~2.5GB(WebP) | 크레딧 소모                | 10GB까지 무료                  |
| 대역폭             | 크레딧 소모                | **무제한 무료**                |
| 변환               | **과금 대상**              | **개념 자체가 없음**           |

**R2에는 transformation이라는 항목이 없습니다.** 이미지 파이프라인이 아니라 순수
객체 저장소라 처리할 것이 없고, 따라서 과금할 것도 없습니다. 초과하더라도 업로드
5.7만 건은 1회성 약 $0.25입니다(100만 건당 $4.50 기준).

**WebP 변환은 로컬에서 수행합니다.** 원본 4.47GB가 이미 있으므로 맥에서 변환한 뒤
완성된 파일만 올립니다. 스토리지 서비스가 처리에 관여하지 않는 것이 핵심입니다.

### 반드시 지킬 절차

위 수치는 공개된 정가표 기준이며 **가입 시 직접 확인해야 합니다.** 지난번에 정확히
이 지점에서 사고가 났으므로:

- [ ] **소량(100건 내외)을 먼저 올리고 대시보드의 사용량 소진율을 확인**한다
- [ ] 예상과 일치하는 것을 확인한 뒤에만 전량을 올린다
- [ ] 업로드 중에도 사용량을 주기적으로 확인한다

## 7-e. 표지 가공 스펙 (D3 확정 · 2026-09-07)

**결정: 500px 단일 · WebP q85(smartSubsample) · 단 WebP가 30dB 미만인 표지는 원본 JPEG를 그대로 사용.**

### 왜 500px 한 종류인가

원본이 전부 `cover500`이라 그보다 큰 것을 만들 수 없고, 목록·카드용 200px을
따로 두는 실익이 작습니다. 프론트가 이미 `sizes` 속성으로 브라우저에 축소를
맡기고 있고, 지금도 알라딘 cover500을 그대로 쓰므로 **현상 유지만 해도 후퇴가
아닙니다.** 단수를 늘리면 저장 용량과 업로드 횟수가 배로 듭니다.

### WebP를 전면 적용하지 않은 이유 — 4:2:0 강제

원본의 **58%가 4:4:4**(색차 풀 해상도)인데 **WebP 손실 압축은 4:2:0을
강제합니다.** 색과 선이 촘촘한 표지에서 화질이 구조적으로 무너지며,
**품질 파라미터로는 회복되지 않습니다.**

고밀도 표지 실측 — q를 올려도 PSNR이 멈춰 있고 용량만 늘어납니다.

| ISBN            | q80           | q85           | q90           | q95            |
| --------------- | ------------- | ------------- | ------------- | -------------- |
| `9791143002549` | 22.6dB / 48KB | 22.7dB / 54KB | 22.8dB / 62KB | 22.8dB / 77KB  |
| `9788901234649` | 25.9dB / 56KB | 26.2dB / 65KB | 26.3dB / 78KB | 26.4dB / 101KB |

같은 표지를 4:4:4로 인코딩하면 28~34dB이 나옵니다. **즉 손실의 원인은 압축률이
아니라 색차 서브샘플링입니다.**

### 대안 비교 (표본 200건, 용량 구간별 추출)

| 변환                    | 평균 크기 | 절감    | PSNR 중앙 | 30dB 미만 | 전체 추정 |
| ----------------------- | --------- | ------- | --------- | --------- | --------- |
| webp q85                | 47KB      | 44%     | 37.4dB    | 20/200    | 2.49GB    |
| webp q85 smartSubsample | 49KB      | 41%     | 38.2dB    | 17/200    | 2.60GB    |
| mozjpeg q82 4:4:4       | 65KB      | 22%     | 36.1dB    | 3/200     | 3.46GB    |
| mozjpeg q90 4:4:4       | 88KB      | **-5%** | 40.6dB    | 0/200     | 4.66GB    |
| 원본 유지               | 84KB      | 0%      | 무손실    | 0         | 4.43GB    |

mozjpeg 재인코딩도 검토했으나 **q90은 원본보다 큰 파일을 만들고**(-5%), 낮추면
화질 이점이 사라져 어중간했습니다.

### 채택한 방식 — WebP + 원본 폴백

변환할 때 PSNR을 재고, **30dB 미만이면 그 한 장은 원본을 그대로 씁니다.**
재인코딩하지 않으므로 손실이 0이고, 오늘 사용자가 보는 파일과 **바이트 단위로
동일**해 어떤 표지도 화질이 후퇴하지 않습니다.

실측(표본 801건, 전체에서 고르게 추출):

|           | 건수        | 평균 크기 | 화질                      |
| --------- | ----------- | --------- | ------------------------- |
| WebP q85  | 752 (93.9%) | 47KB      | 중앙 38.3dB · 최저 30.1dB |
| 원본 유지 | 49 (6.1%)   | 148KB     | **무손실**                |

- 전체 추정 **4.38GB → 2.84GB (35% 절감)**, R2 무료 10GB의 28%
- 원본 유지로 넘어간 49건은 **전부 4:4:4**였습니다. 진단과 정확히 일치합니다.

> **이 결정은 되돌릴 수 있습니다.** 원본을 보관하므로 스펙이 마음에 들지 않으면
> 언제든 다시 뽑으면 됩니다. Phase 0의 "원본을 무가공으로 보관한다" 원칙이
> 여기서 효과를 냅니다. 되돌릴 수 없는 것은 원본 확보뿐이었습니다.

### 변환은 반드시 로컬에서

스토리지 서비스에 이미지 처리를 맡기지 않습니다. **업로드가
transformation으로 계수돼 무료 한도를 2배 초과한 것이 과거 Cloudinary 사고의

## 7-g. 표지 도메인 결정 근거 (D2 확정 · 2026-09-09)

`books.image`에는 `https://cdn.bookjeok.com/covers/{isbn}.{webp|jpg}`가 들어갑니다.

### 기각한 대안

| 안                                  | 기각 사유                                                                                                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pub-<id>.r2.dev` (R2 기본 도메인)  | **「확정된 결정」 2번을 정면으로 위반합니다.** 벤더 도메인을 6만 행에 다시 박는 것이고, 이번 사고의 원인이 정확히 그것이었습니다. Cloudflare도 r2.dev는 개발용이라며 프로덕션에 권장하지 않습니다 |
| `bookjeok.com/api/cover/...` 프록시 | 도메인은 우리 것이지만 모든 표지 트래픽이 Vercel 함수를 통과합니다. R2의 무료 egress라는 최대 장점을 버리고 Vercel 대역폭·실행시간 과금을 자초합니다                                              |

### 커스텀 도메인이 유리한 이유

- `bookjeok.com`의 네임서버가 **이미 Cloudflare**(`christian.ns.cloudflare.com`)라
  R2 대시보드에서 도메인만 입력하면 CNAME이 자동으로 생성됩니다. Vercel 쪽 DNS
  설정은 필요 없습니다.
- 커스텀 도메인으로 나가면 Cloudflare CDN 캐시를 타므로, **캐시 히트는 R2
  Class B 작업으로 계수되지 않습니다.** r2.dev보다 과금 노출이 오히려 작습니다.
- 나중에 R2를 떠나더라도 **DNS만 바꾸면 됩니다.** `books.image` 6만 행은
  건드리지 않습니다. 이것이 「확정된 결정」 2번의 목적입니다.

## 8-c. 검색 랭킹 — 인기도 신호 확보 (2026-09-09)

**문제: "키워드는 맞는데 스테디셀러·인기책이 안 나온다."**

자체 DB 검색으로 전환한 뒤의 체감 품질 문제입니다. 알고리즘을 의심했지만
실측 결과 **원인은 인기도 신호의 부재**였고, 알라딘이 살아 있는 동안에만
해결할 수 있는 문제였습니다.

### 무엇이 잘못돼 있었나

검색 정렬은 `관련도 버킷 → viewCount DESC → isbn`입니다. 그런데 흔한 키워드는
대부분 하나의 버킷에 뭉칩니다.

| 검색어 | 제목 완전일치 | 접두일치 | 부분일치 |
| ------ | ------------- | -------- | -------- |
| 사랑   | 2             | 249      | **791**  |
| 역사   | 0             | 105      | **992**  |
| 우주   | 0             | 61       | 196      |

**즉 두 번째 키인 `viewCount`가 사실상 체감 순서를 결정합니다.** 그런데 그 값은
신호가 아닙니다 — 도서의 **75.7%(43,001건)가 0회**이고, 평균 0.60에 최대 381입니다.
값이 있는 것도 대부분 크롤러가 연관도서 링크를 타고 다닌 흔적입니다(7-b).

참여 신호로 보정하는 길도 막혀 있었습니다. 독서기록 37종 · 위시리스트 32종 ·
리뷰 71종 · 판매글 27종으로 **전체의 0.1%**입니다.

### 실측 — 랭킹이 인기도와 음의 상관이었다

"사랑" 제목 접두일치 251건을 전량 `ItemLookUp`으로 조회해 대조했습니다.

| 현재 랭킹 상위                     | 조회수 | 판매지수 |
| ---------------------------------- | ------ | -------- |
| 사랑이 있는 곳에 신도 있다(초판본) | 93     | 2,463    |
| 사랑이 있는 곳에 신이 있다         | 29     | **30**   |
| 사랑의 메신저                      | 2      | **27**   |

| 판매지수 상위                    | 조회수 | 판매지수 |
| -------------------------------- | ------ | -------- |
| 사랑해 사랑해 사랑해             | **1**  | 59,818   |
| 사랑의 기술 (에리히 프롬)        | **1**  | 38,037   |
| 사랑을 무게로 안 느끼게 (박완서) | **0**  | 6,367    |

스테디셀러가 전부 `조회수 0~1`이라 **바닥에 깔려 있었습니다.** 판매지수가 0인
도서는 251건 중 10건뿐이라 커버리지도 충분했습니다.

### 조치

1. **`books.salesPoint` 컬럼 추가** — DDL 6번. 알라딘 종료 후 재수확 불가
2. **검색 2순위 정렬을 `viewCount` → `salesPoint DESC NULLS LAST`로 교체**
3. **`findPopularBooks()` 개편** — 아래

`findPopularBooks()`는 후보 조건이 `viewCount > 0 OR 활동있음`이라 **도서의 75%가
후보에서 통째로 빠지고 있었습니다.** 조건을 `salesPoint > 0 OR 활동있음`으로 바꾸고
점수식을 이렇게 두었습니다.

```
독서기록×10 + 위시리스트×8 + 리뷰×5 + LN(salesPoint + 1)
```

판매지수는 0~6만 범위라 그대로 더하면 활동 신호를 덮어버립니다. 자연로그를 씌우면
0~11로 눌려서 **최다 판매 도서 한 권이 독서기록 한 건과 비슷한 무게**가 됩니다.
독서 커뮤니티이므로 우리 사용자의 활동이 시장 인기도보다 위에 있어야 하고,
활동이 없는 나머지 5만여 권의 순서는 판매지수가 가릅니다.

### 함께 수확한 것 (지금은 미사용)

`customerReviewRank`(평점)와 `categoryName`(분류)도 같이 받아 JSONL에 남겼습니다.
DB에는 넣지 않았습니다. **재수확이 불가능하므로 받아만 두고**, 필요해지면 재조회
없이 그 파일에서 채웁니다. `categoryName`은 카테고리 필터나 연관 도서 개선에
쓸 수 있습니다.

### 한계 — 이것은 얼어붙는 스냅샷이다

판매지수는 **2026-10-30에 고정**됩니다. 그 뒤 출간되는 책은 값이 없고, 기존 값도
갱신되지 않습니다. 알라딘의 판매지수 자체가 최근 판매에 가중된 값이라 시간이
지날수록 실제와 벌어집니다.

**지속 가능한 대체재는 도서관 정보나루 대출 통계입니다(미결 D5).** 무료·공개이고
한국 도서에 특화돼 있으며 끊기지 않습니다. 대출 통계는 스테디셀러의 정의에 오히려
더 가깝습니다. 다만 마감이 있는 쪽을 먼저 처리하는 것이 맞아 판매지수 수확을
선행했습니다. **D5는 이제 "있으면 좋은 것"이 아니라 판매지수의 후속 계획입니다.**

`pubDate`와 함께 보면 판매지수의 노화를 일부 상쇄할 수 있습니다 — 오래된 책인데
판매지수가 높으면 그것이 스테디셀러입니다.

### 수확·반영 결과 (2026-09-09 완료)

| 항목          | 값                                                          |
| ------------- | ----------------------------------------------------------- |
| 조회          | 56,836건 / 157.9분                                          |
| **수확 성공** | **56,675 (99.7%)**                                          |
| 판매지수 확보 | 56,675 — 그중 값이 0인 것 3,369 (알라딘의 실제 값)          |
| 미확보        | 제목 불일치 148 · 파싱 실패 8 · 알라딘에 없음 5 = **161건** |
| **DB 반영**   | **56,675행**                                                |

미확보 161건은 `salesPoint`가 NULL로 남아 검색에서 `NULLS LAST`로 밀립니다.
**제목 불일치 148건은 결함이 아니라 안전장치입니다** — 알라딘이 다른 책을 돌려준
경우라, 받았으면 엉뚱한 판매지수가 들어갔습니다.

수확 중에 **이어받기 결함**을 발견해 고쳤습니다. `loadDone()`이 결과 종류를 보지
않고 ISBN만으로 완료 처리해서, 일시적 오류로 실패한 행이 재실행해도 영영
재시도되지 않았습니다. 1차 실행의 실패 200건이 그 상태였고, 고친 뒤 재실행으로
**192건을 회수**했습니다. 남은 8건은 알라딘 응답 자체가 파싱 불가입니다.
10/30 델타 재수집에서 똑같이 물릴 결함이었습니다.

### 반영 후 검색 결과 (운영 실측)

| 검색어 | 이전 1위 (viewCount)       | 지수  | 이후 1위 (salesPoint)    | 지수   |
| ------ | -------------------------- | ----- | ------------------------ | ------ |
| 역사   | 역사, 경영에 답하다        | 168   | **역사의 역사**          | 39,508 |
| 사랑   | 사랑이 있는 곳에 신도 있다 | 2,628 | **사랑해 사랑해 사랑해** | 59,821 |
| 우주   | 우주맘의 사계절 유아식     | 3,252 | 우주의 속삭임            | 4,230  |

인기책(`findPopularBooks`)도 크롤러가 훑은 무작위 도서에서 『백야』『월든』
『1984』『댈러웨이 부인』처럼 실제로 읽히는 책으로 바뀌었습니다.

### 성능 실측 — 회귀 없음

| 대상                              | 결과                                                                 |
| --------------------------------- | -------------------------------------------------------------------- |
| `findPopularBooks`                | **61.8ms** (후보 53,306행, top-N heapsort). 09-08의 51ms와 같은 수준 |
| 검색 2글자 (`사랑`·`역사`·`우주`) | **300ms → 300ms.** 정렬 키 교체는 비용 중립                          |
| 검색 3글자 이상                   | 0.16~0.25ms                                                          |

후보가 14,236행에서 53,306행으로 늘었지만 `LIMIT 10`을 top-N heapsort로 처리해
비용이 거의 늘지 않았습니다. 2글자 검색의 300ms는 `pg_trgm`이 2글자에서 인덱스를
쓰지 못하는 **기존 한계**이며 이번 변경과 무관합니다(전후 동일). 8장 참조.

### 아직 하지 않은 것

- **`similarity()` 도입.** pg_trgm 인덱스는 지금 `ILIKE` 가속에만 쓰이고 랭킹은
  9단계 CASE입니다. `similarity(title, q)`는 연속값이라 제목 길이 정규화가 자동으로
  됩니다(짧은 제목이 위로). 버킷이 굵어서 생기는 문제는 남아 있습니다.

## 8-d. 출판사 검색이 전집 세트에 막히던 문제 (2026-09-09)

판매지수를 넣은 뒤 `"민음사"`를 검색했더니 **민음사 세계문학전집 세트가 1페이지를
독점**했습니다. 알라딘 결과와 확연히 달랐습니다.

### 판매지수 문제가 아니었다

세트 12권이 `203 > 193 > 125 > 102` 순으로 정렬돼 있었습니다. 판매지수는
정상 작동하고 있었고, 문제는 그 **위의 관련도 버킷**이었습니다.

| 버킷                  | 건수    | 최대 판매지수 |
| --------------------- | ------- | ------------- |
| 1 제목 접두일치       | 12      | 203           |
| 2 제목 부분일치       | 1       | 9,288         |
| 4 저자 접두일치       | 12      | 12,575        |
| **6 출판사 완전일치** | **814** | **319,512**   |

관련도 CASE가 **필드 우선**(제목 3단계 → 저자 3단계 → 출판사 3단계)이라,
제목에 "민음사"가 든 12권이 출판사가 민음사인 814권을 무조건 이겼습니다.
판매지수는 버킷 안에서만 순서를 가르므로 이 구조는 판매지수로 고칠 수 없습니다.

**판매지수 도입 전부터 있던 결함이며, 인기도 신호가 생기면서 비로소 눈에 띄었습니다.**

### 조치 — 출판사 완전일치만 승격

`relevanceCaseSql`의 순위를 아래로 바꿨습니다.

```
0 제목 완전일치
1 출판사 완전일치   ← 승격
2 제목 접두일치
3 제목 부분일치
4 저자 완전일치
5 저자 접두일치
6 저자 부분일치
7 출판사 접두일치
8 출판사 부분일치
```

출판사명을 그대로 친 검색은 "그 출판사 책을 보여달라"는 뜻이지, 제목에 그 말이
든 책을 찾는 것이 아닙니다.

### 저자를 함께 승격하지 않은 이유

같은 논리를 저자에도 적용하면 오히려 나빠집니다. **저자 표기가 섞여 있기
때문입니다.**

| 필드        | 괄호 포함       | 비고                                         |
| ----------- | --------------- | -------------------------------------------- |
| `author`    | **7,497 (13%)** | `(지은이)` 6,494 · 다중저자 표기 8,405 (15%) |
| `publisher` | 2,229 (4%)      | 고유 출판사 5,911종                          |

김영하의 책은 `김영하 (지은이)` 9권과 `김영하` 4권으로 나뉘어 있습니다. 저자
완전일치를 승격하면 **표기 차이만으로 한 저자의 책이 갈라집니다.** 실측에서도
`오래 준비해온 대답`(13,015)이 밀려났습니다. 출판사는 오염도가 4%뿐이라
같은 문제가 없습니다.

### 실측 (운영 DB)

| 검색어                                        | 이전 1위                            | 이후 1위                      |
| --------------------------------------------- | ----------------------------------- | ----------------------------- |
| 민음사                                        | 민음사 세계문학전집 K세트 (203)     | **싯다르타 (319,512)**        |
| 창비                                          | 창비교육 중학교 국어 자습서 (7,135) | **소년이 온다 (318,268)**     |
| 문학동네                                      | —                                   | **안녕이라 그랬어 (257,607)** |
| 김영하 · 채식주의자 · 역사 · 그리스 로마 신화 |                                     | **변화 없음**                 |

페이지네이션도 다시 확인했습니다 — "민음사" 5쪽 100건에 중복 0.

홈 화면의 출판사 슬라이더와 도서 상세의 "같은 출판사 책"이 같은 경로를 타므로
함께 개선됩니다.

### 남은 한계

버킷이 굵다는 문제 자체는 그대로입니다. `similarity()` 도입은 여전히 미완이며
(8-c) 제목 길이 정규화가 필요한 경우를 덜어 줍니다.

## 9-c. 코드 점검 결과 (2026-09-08)

마이그레이션으로 도서 도메인을 여러 번 고쳤으나 한 번도 점검하지 않아, 서버
도서 모듈 전체를 리뷰했습니다. 두 진단(자체 리뷰 + 외부 모델)을 교차 검증했고,
운영 DB로 확인 가능한 것은 전부 실측했습니다.

### 고친 것

| 대상                    | 문제                                                                                                                                  | 처리                                                        |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `resolveBook()`         | ISBN 검색 폴백이 **제목에 남의 ISBN이 박힌 책과 오매칭**되어, 등록이 404 대신 **FK 위반 500**(`reading_logs`는 FK가 없어 **고아 행**) | 폴백 제거. "찾거나 404"인 5줄 가드로 축소                   |
| `resolveBook()`         | 미존재 ISBN마다 동일한 `findOneBy`를 2회 + 무의미한 ILIKE 1회 = 쿼리 3회                                                              | 1회로                                                       |
| `findPopularBooks()`    | ORDER BY의 상관 서브쿼리가 후보 행마다 실행 (14,236행 × 3 = 42,708회 스캔)                                                            | 활동 테이블을 GROUP BY로 압축해 LEFT JOIN. **442ms → 51ms** |
| `LocalDb.search()`      | `query=" "` 한 칸이 `ILIKE '% %'`가 되어 **57,577행 매칭 / 카운트에만 3초**                                                           | `trim()` 판정                                               |
| `BookCatalogService`    | `display=-1` → `LIMIT must not be negative` **500**. 상한도 없어 `display=100000`이 그대로 통과                                       | 1~100 클램핑                                                |
| `findPopularBooks()`    | `addSelect` 3개가 뒤의 `select(배열)`에 덮여 SQL에 들어가지도 않음                                                                    | 제거                                                        |
| `book.module.ts`        | 알라딘 서비스 삭제 후 `HttpModule`이 주입처 없이 잔류                                                                                 | 제거                                                        |
| `dtos/book-info.dto.ts` | 참조 0건. `@IsNotEmpty(pubdate)`·`@IsUrl(image)`가 현행 모델과 상충                                                                   | 삭제                                                        |
| 주석 5곳                | "검색은 외부 공급처 우선", "없으면 외부 API로 생성", "검색 체인에서는 아직 마지막", "books에 pubDate 컬럼이 없고" 등                  | 현행에 맞춤                                                 |

### 정정 — 심각도를 과장했던 것

`GET /book/popular`을 처음에 "4.9초"로 보고했으나, **그것은 콜드 캐시 1회
측정치**였습니다. 웜 상태에서 재보니 **442ms**입니다. 그리고 홈·마켓 페이지가
`revalidate = 3600`으로 ISR 캐시하므로 사용자가 그 시간을 기다리지도 않습니다.

고칠 가치는 여전히 있었지만(442ms → 51ms), **"공개 엔드포인트가 5초씩 멈춘다"는
표현은 부정확했습니다.** 성능 수치는 웜/콜드를 구분해 여러 번 재고 보고하세요.

### 사실이 아니었던 지적

외부 진단에 "파이프가 인터셉터보다 먼저 실행되어 24시간 캐시가 무력화된다"는
항목이 있었으나 **순서가 반대**입니다. NestJS는 인터셉터 → 파이프 → 핸들러이고
`BaseViewCountInterceptor`는 `next.handle()` **앞에서** 캐시를 확인합니다.

다만 인터셉터가 `next.handle()`을 항상 호출하므로 **파이프의 DB 조회는 캐시
적중과 무관하게 매번 실행**됐습니다. 원인은 틀렸고 낭비는 실재했습니다.
그리고 인터셉터가 먼저 돌기 때문에 **존재하지 않는 ISBN에도 조회수 증가를 시도하고
24시간 캐시 키를 심습니다**(`increment`가 0행이라 에러는 안 남).

**처리:** `POST /book/:isbn/view`에서 `BookResolvePipe`를 제거했습니다.

애초에 필요 없는 자리였습니다. 그 파이프는 `books`를 참조하는 행을 만들기 전에
외래키 위반을 막는 가드인데, 이 경로는 `viewCount`를 올릴 뿐 참조 행을 만들지
않습니다. 없는 ISBN이면 `increment`가 0행으로 끝나는 무해한 no-op입니다.

|           | 이전            | 이후           |
| --------- | --------------- | -------------- |
| 캐시 적중 | SELECT 1회      | **0회**        |
| 캐시 미스 | SELECT + UPDATE | **UPDATE 1회** |

외부 진단은 "인터셉터가 `affected === 0`이면 404를 던지도록 단일화"를 제안했으나
채택하지 않았습니다. `BaseViewCountInterceptor`를 **3곳이 상속**하고(도서·중고
판매글·리뷰) `incrementCount`가 전부 `Promise<void>`라, 도서 하나 때문에 공용
기반 클래스의 계약을 바꿔야 합니다. 게다가 프론트가 `recordBookView(isbn).catch()`로
**실패를 무시**하므로 404를 던져도 사용자에게 아무 차이가 없습니다.

남는 문제는 없는 ISBN에 캐시 키가 심기는 것뿐인데, 캐시가 인메모리라 이론상
증가 요인입니다. 다만 알라딘 제거로 **크롤 공간이 이미 닫혀** 없는 ISBN 트래픽
자체가 드뭅니다. 실제로 관측되면 그때 `BookViewCountInterceptor` 안에서
"0행이면 캐시를 심지 않기"로 처리하면 되고, 기반 클래스는 건드리지 않아도 됩니다.

### 지금 하지 않기로 한 것

**`reviews.isbn`·`wishlists.isbn` 인덱스 추가.** 세 활동 테이블이 41·76·49행뿐이라
Postgres가 인덱스가 있어도 Seq Scan을 택합니다(`reading_logs`엔 `(isbn, date)`
인덱스가 있는데도 그렇습니다). 단건 실행이 2~6ms라 지금 규모에선 효과가 없습니다.
데이터가 커지면 그때 재검토하세요.

## 9-b. 운영 환경과 작업 도구

세션이 바뀌어도 같은 시행착오를 반복하지 않도록, 이 작업에 필요한 환경 정보를

### 작업 머신이 두 대입니다 (중요)

|                                                                                         | 맥       | 윈도우                |
| --------------------------------------------------------------------------------------- | -------- | --------------------- |
| `apps/server/.env.prod.local` (운영 DB 접속)                                            | **있음** | 없음                  |
| 마이그레이션 작업 폴더 `~/bookjeok-migration/` (스크립트·데이터·자격증명·표지 원본 tar) | **있음** | 없음                  |
| 셸                                                                                      | zsh/bash | PowerShell + Git Bash |

**운영 DB를 향한 스크립트는 맥에서 돌리는 것이 기본입니다.** 윈도우에서 돌리려면
접속 문자열을 환경변수로 직접 넣어야 합니다.

```bash
# 맥 — .env.prod.local을 읽어 쓰면 됩니다
set -a; source apps/server/.env.prod.local; set +a
pnpm --filter @bookjeok/server exec ts-node scripts/<스크립트>.ts
```

```bash
# 윈도우(PowerShell) — 접속 문자열을 직접 지정
$env:SEARCH_DATABASE_URL='<접속 문자열>'; pnpm --filter @bookjeok/server exec ts-node scripts/<스크립트>.ts
```

측정·조사 스크립트는 접속 문자열을 출력하지 않습니다(호스트명만 찍습니다).
결과는 그대로 공유해도 되지만 **접속 문자열 자체는 대화에 붙여넣지 마세요.**

### 운영 DB 접속

- 접속 문자열은 `apps/server/.env.prod.local`의 `SURVEY_DATABASE_URL`에 있습니다
  (gitignore 대상, 권한 600).
- **직접 연결(`db.<ref>.supabase.co`)은 쓸 수 없습니다.** AAAA 레코드만 있는
  IPv6 전용 호스트인데 이 개발 머신에 전역 IPv6가 없습니다.
- **Supabase 풀러(`aws-1-ap-northeast-2.pooler.supabase.com:5432`)로 접속합니다.**
  사용자명이 `postgres.<project-ref>` 형태인 점에 주의하세요.
- 조회는 항상 읽기 전용 트랜잭션으로 여세요. `scripts/survey-book-covers.ts`가
  그 형태의 참고 구현입니다.

### 배포 흐름

- `develop` → `main`을 **Pull Request로 병합**합니다(main 이력이 merge commit).
- **이 머신에 `gh` CLI가 없습니다.** 에이전트가 PR을 만들 수 없으니 링크만
  제시하고 사용자가 생성해야 합니다: `https://github.com/Yoo-su/bookjeok/compare/main...develop`
- 필요하면 `brew install gh && gh auth login`으로 설치할 수 있습니다.
- **저장소는 공개입니다.** 외부 CDN을 대량으로 긁는 코드 등은 커밋 전에 공개
  적절성을 따로 판단하세요(7-d·8-b 참조).

### 운영 확인

배포 후 실제 페이지로 확인합니다. 로컬에는 DB도 docker도 없어 통합 실행이
불가능합니다.

**맥에만 있습니다.** 둘 다 gitignore 대상이라 저장소에는 없습니다.
